# 第二个用户 prompt:fail-fast 还是排队

> 状态:proposed · 提出 2026-09-01 · 来源 [Lifecycle 与 Run Loop](../../design/lifecycle-and-run-loop.md) §9

## 现状

run 进行中,`prompt()` **同步抛 busy**;而 inbox 的工作会**排队**等 foreground permit。两种入口的队列语义不同,这个差异已有测试保护。

## 不拍板的代价

这是产品语义,不是实现细节。使用者写 UI 时必须知道第二次提交会被拒绝还是会排队——猜错就会做出错误的交互(比如禁用输入框 vs 显示排队中)。

## 选项

- **A. 保持 fail-fast。** 调用方自己决定重试或提示。代价:每个 UI 都要处理 busy 异常。
- **B. 与 inbox 一致,排队。** 代价:需要定义队列深度、超时、以及「排队中被 abort」的语义。
- **C. 由构造参数选择。** 代价:又多一个由构造参数暗中改变方法行为的地方——与本仓已有的另一个问题同源(见 start-precondition)。

## 验收
