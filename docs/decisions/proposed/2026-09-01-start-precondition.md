# `start()` 是否所有 Agent 的统一前置条件

> 状态:proposed · 提出 2026-09-01 · 来源 [Lifecycle 与 Run Loop](../../design/lifecycle-and-run-loop.md) §9

## 现状

取决于构造时注入了什么:注入 `stateLock` 或 session service 后进入 lifecycle-managed 模式,未运行时拒绝新工作;裸 `new Agent()` 可以在 `new` 阶段直接 `prompt()`,且已有测试明确保护这个行为。`createEcho()` 不自动启动,宿主必须显式 `start()`。

## 不拍板的代价

**方法的前置条件由构造参数暗中决定,调用方无法从类型上看出来。** 文档也因此写不出一句准确的通则——既不能说「用前必须 start()」,也不能说「构造后即可 prompt」。

## 选项

- **A. 统一要求 `start()`。** 裸 Agent 也要显式启动。代价:低层使用多一步,已有测试要改。
- **B. 保留两种高度,但拆成不同的构造入口。** 例如 `new Agent()` 与 `createManagedAgent()`,前置条件写进类型。代价:公共面多一个入口。
- **C. 维持现状,在文档里说明。** 代价:类型面继续沉默,读者只能靠文档。

## 倾向

文档指出:如果这是有意保留的两个使用高度,**必须给它们不同的名字或不同入口**,不能靠构造参数暗中改变前置条件。

## 决定

待拍板。

## 验收

从公共类型能看出某个 Agent 是否需要 `start()`;或公开文档有一句无例外的通则。
