# 记忆提取降频：用户说的话攒够才跑，只看上次提取之后的新内容

> 状态:implemented · 提出 2026-10-30（用户反馈后台提取太频繁；对照 Claude Code 2.1.314 的提取门控）· 拍板 2026-10-30（用户，两步方案的第 1 步）· 落地 `packages/core/src/memory/extract.ts` / `agent.ts`，判据 `packages/core/test/memory-extract.test.ts`、`packages/core/test/create-echo.test.ts` · 修改 [每条 reply 结束跑一次提取](2026-09-07-memory-extraction.md) 的触发与输入

**给谁看**：改记忆提取的触发、输入或成本的人。假设已知 [提取的原始决策](2026-09-07-memory-extraction.md) 与 [记忆设计](../../design/memory.md) §5。

## 现状（拍板前）

每条 reply 结束都跑一次提取，跳过条件只有三种：这轮前台写过记忆、一个模块都没有、上一次还在跑（折叠）。没有「这轮有没有新东西」的判断，「谢谢」「OK」也各跑一次。每次都把整段 working context 重发一遍，工具结果也是全文，单次成本随会话长度线性增长。

实测（真实 `echo-coding` + DeepSeek，6 句管道对话）：3 次提取、5 次模型请求、**0 条写入**，占全部未命中输入的 48%、全部输出的 42%。

参照（只看机制，不作设计依据）：Claude Code 同样在每轮回复结束触发，但调模型前有用户正文门槛、每 N 轮、空闲补跑、先问一句、超额跳过等几道门；只看游标之后的新消息；从主对话分叉跑，复用主对话的缓存。

## 选项

- **A. 用户正文门槛 + 游标**：数自上次提取以来用户说了多少话，没够不跑；只把游标之后的新内容给提取。
- **B. 空闲触发**：对话停下若干秒才跑。管道 / 评测形态等不到空闲就退出，交互形态退出前的最后一段会丢。
- **C. 每 N 条 reply 一次**：不看内容。
- 另一步（不在本条）：提取从主对话分叉跑，复用主对话缓存。

## 决定

**A**（2026-10-30 用户拍板，两步方案的第 1 步）。五条：

1. **门槛只数用户亲口说的**：`human` / `steer` 的用户消息正文（`userProseWords`）。中日韩文字一字一词，其余按空白分词、纯标点不算。助手回复、工具输出、harness 插话、环境消息都不算——「谢谢」之前助手可能刚读完一个大文件，按全部新内容算照样会触发。阈值 `DEFAULT_EXTRACT_MIN_USER_WORDS = 8`，首版估计（滤掉致谢 / 确认），实测后再调。
2. **没过门槛就攒着，游标不动**。拍板时的说法是「跳过并把游标推过去」，实现时改成攒着：前台埋头干活时踩到的坑正是原始决策点名要记的，而那时用户往往只说一句「继续」——推过去这段就再没人看。攒着的话，它随下一条过门槛的话一起被看到；省下的调用次数相同。代价：会话结束时没攒够的那一截不提取。
3. **游标**：transcript 下标，`[0, cursor)` 算已看过。压缩只改视图不改 transcript，游标照样有效。只在提取**正常跑完**时推进到这次材料的末尾；出错、轮数用完、被中止都不动，下次重看。前台这轮写过记忆：游标直接推过这一段（前台处理过了），不提取。
4. **材料定格在 reply 边界，起点在跑时读**：排队期间前一次提取可能已推进游标，跑的那一刻从游标读起，再判一次门槛。`reset` 归零、续会话设到末尾（不回头看上个进程的历史），两者都换一代：在飞的旧提取不推游标。
5. **提取只看游标之后**：`projectRange(transcript, compaction, cursor, end)` 投影后渲染，被压掉的部分以摘要 / 占位出现。prompt 里说明这是「上次之后的部分」。

## Non-Goals

- 不做空闲补跑、每 N 轮、先问一句：等本条的数据出来再议。
- 不改提取的模型、轮数上限、工具面；提取从主对话分叉复用缓存是第 2 步，另议。
- 游标不落盘：续会话时直接设到末尾。
- 不改重叠保护「本 reply 出现成功的 memory 工具结束事件」的口径（`view` 也算），只把它的效果从「跳过」表达成「推过游标」。
- 门槛不做成产品配置。
