# 记忆文件的并发:跨进程文件锁,锁的范围是「读到写」整段;`stop()` 等两个后台通道收完再交 lease

> 状态:implemented · 提出 2026-09-07 · 拍板 2026-09-07(口头) · 实现并合入 2026-09-08 · 偿还 [会话与 agent 集群](../../design/sessions.md) Non-Goals 里挂着的「memory 目录的多写者保护,归 memory 线」

## 现状(拍板前)

记忆文件的写全部是直接 `dir.write`。`FileDir` 走 tmp + rename,所以**文件不会写成半截**;但"读出来—改好—写回"这个序列中间如果别人写了同一个文件,写回会把它盖掉,**一点痕迹都没有**。

今天这属于已知限制:[记忆三级作用域](2026-09-03-memory-three-scopes.md) 明写"project / user 两层的并发写先接受后写覆盖",[会话与 agent 集群](../../design/sessions.md) 的 Non-Goals 把它挂给 memory 线。当时成立的前提是**共享层的写很稀疏**——只有前台模型偶尔记一条。

同一进程内也有一份:`AgentMemories` 上的写方法之间没有互斥。`memory/harness.ts` 里 `dreamStateChain` 那条 `WeakMap` + Promise 链只串行化了 dream 状态的读改写(实测过并发会丢计数),记忆文件本身没有。

## 不拍板的代价

这轮的两个决定同时把前提推翻了:

- [记忆的产生](2026-09-07-memory-extraction.md):每段 session 的每条 reply 都跑一次提取。"两段 session 同时往同一层写"从罕见变成常态。
- [dream 改造](2026-09-07-dream-rework.md):dream 现在整理共享层,而它是"读一批、改一批、写回"——中间别人写进来的那条会被它吃掉。从"偶尔撞一次"变成"每次整理都可能丢一条"。

丢失没有任何痕迹:没有报错、没有诊断、没有观测事实,事后查不出来。用户只会发现"我记的那条不见了"。

## 选项

- **A. 只做进程内串行**(Promise 链),跨进程仍是后写覆盖。
- **B. 跨进程文件锁**,锁的范围是一次写。
- **C. 跨进程文件锁**,锁的范围是"读到写"整段。

## 决定

**C**(2026-09-07 用户拍板)。

**范围是"读到写"整段,不是一次写。** B 只防住"两个写同时落盘、文件变成半截"——那件事 tmp + rename 今天已经防住了,B 等于花力气买一个已有的保证。真正咬人的是读改写序列被插队,只有把锁持到写回才挡得住。代价很小:dream 是逐个文件处理的,每个文件持锁就是"读—改—写"这几毫秒。

**跨进程,不只是进程内。** 那把锁是现成的——lease 用的 `fileStateLock` 同款。A 只解一半:提取上线之后,两段 session 同时往 user 层写会是日常。

三种保护各管各的,别混:

| 机制 | 管什么 |
|---|---|
| tmp + rename(已有) | 文件不会是半截内容 |
| **文件锁**(本条) | 读改写序列不被插队,谁的修改都不会被静默盖掉 |
| 整理锁(按层,[dream 改造](2026-09-07-dream-rework.md)) | 两个 dream 不把同一层各重排一遍——省功,不是正确性 |

**拿不到锁的一方跳过,不重试。** dream 的 prompt 里因此有一句"某个文件改不动就跳过、别反复重试":整理是 best-effort,下一轮还会来;为一个文件把整次整理堵在那里不值得。

### `stop()` 要等两个通道收完才交出 lease

两个后台通道不进 admission 之后,没有 `admission.abortMaintenance()` 帮忙收这一步了,得各自带一个 abort + 等待,挂进 `stop()` 的收摊链。

理由不是整洁,是 lease 的定义:**只要这个进程还在往记忆里写,锁就不能交出去**。今天 dream 那条收摊(`settleDream()`)存在正是因为踩过——注释记着"不等的话,租约已经归别人、旧 dream 还在往 memory 里写,单写者当场破",是实测出来的。租约不区分写者是主循环还是后台通道。

不能只等 dream 不等提取:"提取短"是概率不是保证,`maxTurns` 限的是轮数,一轮可以卡在一次很慢的模型请求上。

## 验收

- 两个进程各起一段 session,同时对同一层的同一个文件做"读—改—写":两次修改都在,没有一次被静默覆盖。
- dream 正在整理某个文件时,另一段 session 的提取往同一个文件写:一方拿不到锁、跳过,并留下诊断;两边的内容都没坏。
- 同一进程内前台、提取、dream 三个写者并发写同一层:没有丢更新(与 `dreamStateChain` 今天那个丢计数的复现用同一种 barrier 手法构造)。
- 持锁进程被 `kill -9`:锁过期后别的进程能继续,不会永久卡死。
- `stop()` 在提取正跑到一半时调用:lease 释放发生在提取真的收完之后(用一个写到一半就挂起的假模型构造)。
- 拿不到锁不重试:构造一个长期被占的文件,dream 跑完不会卡住,它跳过那个文件并整理了其余的。

**实现注（2026-09-10）。** 上一版的锁挂在 harness 对象上，不同实例之间不互斥；`assertFresh` 的先比后写也不原子——find_job 的并发探针实测两边都报成功、最终丢一边（A B → A BB）。现在：

- `StorageDir` 加可选的 `lock(name)` 原语：`FileDir` 用锁目录（跨实例、跨进程；2026-09-10 起是带递增编号的锁），`InMemoryDir` 实例内互斥；前缀视图、写入闸视图、`sharedUser` 与状态根的包装都原样转发。
- 互斥范围是**层 × 记忆模块**（`<层>/.locks/<模块>`），一次提交的读、改、预算校验、落盘、索引重建整段独占——正文、预算、索引一起被罩住。字节面没有 `lock` 原语时退回按对象的进程内互斥。
- 等不到（缺省 10 秒）返回明确的 `busy` 冲突，不写、不覆盖。

**与验收的那条差异（2026-09-10 已解决）**：验收写「持锁进程被 `kill -9`，锁过期后别的进程能继续」。首版实现按 2026-08-18「不做自动接管陈旧锁」没做，崩在持锁窗口里要人手删锁。同日改成带递增编号的锁，持有者确认已死就自动接管，lease 与记忆提交锁一起换（[决策](2026-09-10-generation-lock-takeover.md)）；判据是 `packages/core/test/memory.test.ts` 里「写者崩在提交中途」那条。

**实现注（2026-09-11）：读完到写回之间。** 提交锁只罩住一次工具调用；模型「读完 → 思考 → 写回」横跨好几次调用，中间别人写过一笔，它凭旧内容整份写回照样吃掉那一笔。改成覆写前核对读到的版本，而不是把锁拉长到整个处理过程（[决策](2026-09-11-memory-read-version-check.md)）。同批：整理按层试拿独占、Dream 计数进短锁。
