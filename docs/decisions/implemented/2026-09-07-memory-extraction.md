# 记忆的产生不再只靠前台自觉:每条 reply 结束跑一次提取,独立异步通道、隔离子 agent

> 状态:implemented · 提出 2026-09-07 · 拍板 2026-09-07(口头) · 实现并合入 2026-09-08 · 相关 [dream 改造](2026-09-07-dream-rework.md)(整理是另一件事)、[记忆的并发](2026-09-07-memory-concurrency.md)(两个通道共用的锁)

## 现状(拍板前)

记忆只有一条写入路径:**前台模型自己想起来**。core 的 [`renderMemorySystem`](../../../packages/core/src/memory/compose.ts#symbol=renderMemorySystem) 出一段规则(模块说明、选层说明、"写前先找能合并的、删过期的、超预算先整理、别记当前任务进度、别存密钥"),`echo-agent` 与 `echo-coding` 两个产品的 prompt 里一个字都没提记忆。

那段规则里**没有一条讲什么时候写**。实测结果:旧位置的 dream 状态记着 `{"writes":3,"turns":320}`——自 2026-09-04 那次整理以来 320 轮对话,记忆写入 3 次,而且三次全发生在冒烟测试当天 02:14,之后是 0。

## 不拍板的代价

只把那段规则写得更强,是在赌"0 次写入的原因是提示词不够"。参照物指向另一个原因:Claude Code 有一个**专门的提取 agent**(`services/extractMemories/extractMemories.ts`,forked、受限权限、`maxTurns: 5`,与主 agent 已写记忆的重叠保护),触发点是 stop hook 上的 fire-and-forget——记忆不是靠前台自觉写的。同一台机器上这个项目的 33 条 CC 记忆全部带 `originSessionId`,说明提取一直在跑;而 `.consolidate-lock` 不存在,说明整理一次都没跑过。**产生比整理重要**,而我们恰好只有整理。

(以上是对本机 2.1.263 二进制与一份第三方逆向文档的核对结果,作为参照物,不作为本仓的设计依据。)

## 选项

- **A. 只把前台那段规则写强**,跑几天看写入计数还是不是 0。
- **B. 加一次提取**:会话收尾时看这轮对话、产出记忆。
- **C. 让 dream 兼做提取**:给现在这个 dream 加上 transcript 的读权限。

## 决定

**A + B**(2026-09-07 用户拍板)。前台自觉保留并把规则写强(见下),**另加**提取。

C 被否:它把两件语义相反的活压进一个 run——提取要读对话、产出新事实;整理明确禁止发明新事实(`memory/dream.ts` 那条 "only reorganize what is already there")。

### 形状

**每条 reply 结束跑一次。** reply 是"agent 对一条输入的完整回应"([Run Loop 的四层](../../design/run-loop-layers.md) §1),是"这轮有结论了"的自然边界。不按 turn:一条 reply 里可能有十几个 turn,turn 级会在工具执行到一半时插进来,那时任务还没有结论,提出来的是半截。不按 run 收尾:一个 run 可能跑很久。

**独立异步通道,不进 admission。** 这是本条最要紧的一处。今天 dream 走 admission 的 maintenance 优先级,前台一来就让位;提取如果照做,用户连着说十句话,十次全被下一条 prompt 抢占,实际提取 0 次——绕一圈回到"320 轮 0 次"。dream 可以被抢占(它整理的是已经落盘的东西,晚一轮无损),提取不行(它要抓的是马上会被压缩掉的上下文)。

单许可不是 core 的架构约束:`admission/types.ts` 写着"RunPermit、并发裁决、失败规范化都是 Host 私有",`AgentAdmissionPort` 是可替换的 host port;挡着的是 `StandaloneRunAdmission` 这一个实现。提取的工作特征也支持并行——短(`maxTurns` 限死)、只碰记忆、独立 context 不动主 transcript、事件不外发,与前台**没有共享可变状态**,唯一交叉是记忆文件(归 [记忆的并发](2026-09-07-memory-concurrency.md))。

**隔离子 agent,全套记忆工具。** 复用 [`runSubagent`](../../../packages/core/src/agent.ts#symbol=Agent.runSubagent)(dream 走的同一条隔离子循环)。给**全套**记忆工具:它可以先 view 再决定、要覆写就 `str_replace`、判断错了还有下一轮纠。`maxTurns: 5`,模型走产品配的便宜档——它是没人看着的后台活,成本必须有硬上界。

**看 working context,塞进 prompt。** `runSubagent` 是独立 context,子 agent 默认什么都看不见。把这次 reply 实际送给模型的那份塞进它的 prompt,而不是给它 `transcript_read` 让它自己找——后者会让它先花两三轮摸索该读哪段,那几轮比直接给还贵,读偏了还白跑。

**不为压缩加联动。** 压缩不是"丢掉"而是"折成摘要":`summary` 阶段产出的九节结构化摘要里有 findings、failures and fixes、the user's messages(逐字)几节,恰好是记忆的原料,而摘要留在 working context 里。所以提取扫送模的那份就够了,被压掉的原文以摘要形态还在它眼前。只有多次压缩后摘要被再次合并时细节才真丢,那本来就是"这些细节已经不重要"的判决。

**往哪层写,与前台同判据。** 它拿到的层清单和 `describe` 与前台是同一份(见 [作用域由产品声明](2026-09-07-memory-scopes-by-product.md) 的「模型怎么知道该往哪层写」)。不做"只写最窄那层、由 dream 往上提"——那是把明确不做的自动提升请回来。

**重叠保护。** 这条 reply 里已经出现过 `memory.mutation.committed` 事实(前台模型自己写过记忆)就跳过这次提取。观测那条线已经在发这个事实(`memory/observe.ts`),不用新造信号。

**被抢占不用补跑。** 提取每次重扫整段 working context,所以中断的那次会被下一条 reply 结束时那次一并看进去。

**不依赖 provider 的结构化输出。** 子 agent 用工具写记忆,没有"一次调用输出结构化结果"这个需求,因此这条线不排在 provider 那条线后面。

### 前台那段规则补什么

今天缺的是"什么时候写"。补两组判据:

- **事件**(管召回率):用户纠正了你或说了他要你怎么做事;你踩了一个下次还会踩的坑(环境怪癖、工具行为与文档不符);一个决定连同它的理由被拍定;一个你只能靠试出来、读不到的事实。
- **持久性**(管准确率):这条在下个月另一段会话里还成立、还有用吗。不成立就丢——这正是今天那句"别记当前任务进度"想表达而没说透的。

再加一条形状要求:每条带一句 description,因为它是将来被召回时唯一的判据。

### 提取 prompt 的骨架

全英文,措辞自行撰写(不抄任何专有产品的文案)。顺序与要点:

1. 先 view 已有的再写——大部分"看起来是新的"已经在里面了。
2. 值得留的四类事件(上一节)。
3. 明确排除:当前任务进度(那是 transcript 的活)、仓库自己已经写着的(布局、代码结构、git 历史、项目指令文件)、只在这段对话里成立的、任何凭据。
4. 每条一个事实;用 "and" 连起来的是两条。每条一句 description,按"它是关于什么"写而不是按名字写。绝对日期,不写"昨天"。
5. 该合并进已有条目时就合并,不新增近似条。
6. 层与模块的清单(它拿不到 system prompt,这份材料必须由 prompt 自带)。
7. **最后一条,最要紧**:什么都不写是正常结果,大多数 reply 不产生记忆,不要为了交差编一条。

第 7 条是提取质量的关键——被派了活就想产出,是记忆变脏的主要来源。

## 验收

- 一条 reply 结束后提取真的跑了:观测里出现它那条 run,且它的事件不进主事件流、主 transcript 一字未变。
- 用户连续发十条 prompt:十次提取都完成(不被抢占),而同期的 dream 被抢占。
- 提取子 agent 的工具面只有记忆工具;`maxTurns` 用满即停,不会无限跑。
- 前台在这条 reply 里写过记忆 → 这次提取直接跳过,不发起模型请求。
- 一段没有任何值得记的对话(闲聊)跑完提取,记忆目录零变化。
- `stop()` 期间在飞的提取被中断并等它收完之后才交出 lease(见 [记忆的并发](2026-09-07-memory-concurrency.md))。

**实现注（2026-09-10）。** 本条「前台那段规则补什么」里的两组判据（事件、持久性）已从 core 的记忆段与提取 prompt **挪进内建模块的 instructions**（主要是笔记模块），core 那三处 prompt 只剩机制。原因：判据是内建模块的语义，不是记忆机制本身的规则——写在 core 里时，产品 `memory.builtin: false` 换掉了模块，coding 味的判据（「下个月另一段会话还成立吗」「只在本对话成立的不记」）却还压在陪伴产品的模块上。现在关掉内建模块会连判据一起拿掉，产品模块用自己的 instructions 带自己的判据。默认用户看到的判据内容不变，只是位置从全局规则挪到了模块说明下面。
