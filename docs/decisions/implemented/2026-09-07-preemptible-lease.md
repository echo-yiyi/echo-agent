# 人优先，后台让位：自称可让位的持有者被请走时交还 lease；不可让位的照旧不抢占

> 状态:implemented · 提出 2026-09-07 · 拍板 2026-09-07(口头) · 合入 2026-09-07(e48a366) · 补记 2026-09-07 领域模型 review(代码先于记录,本条把硬约定的措辞改准)

## 现状(拍板前)

single-writer 的硬约定写作「锁被占着就拒绝启动,core 不抢占、不猜对面死没死」。这对人开的会话是对的:两个终端不该互相顶掉。但常驻程序(findjob 这类)为处理一条消息叫醒的临时实例,和随后要打开同一段的常驻实例或人,是同一产品内的两个实例;临时那个既没有人在用,也没有理由占着不放,而按老规矩后来者只能被拒。

## 不拍板的代价

要么常驻程序自己在 core 外面写一套「先杀临时实例再起」的接管逻辑(与 single-writer 的语义分家),要么每次唤醒都要等临时实例自然收摊。

## 选项

- **A. 持有者可自称「可让位」;拿不到锁的人先问一句。** 可让位写进锁文件,请它走的人可能在另一个进程;只有自称可让位的持有者会收到信号并交还,其余照旧拒绝、人工清锁。
- **B. core 抢占。** 与「不猜对面死没死」直接冲突。
- **C. 不做,由产品在外面接管。**

## 决定

**A**(2026-09-07 用户拍板,e48a366)。**机制在 [会话与 agent 集群](../../design/sessions.md) §5**(谁能自称可让位、写进锁文件的理由、谁去问、让位走哪条收摊路),本条不复述。

选 A 而不是 B / C 的理由:B(core 抢占)与「不猜对面死没死」直接冲突——判断对面是不是死了这件事,core 没有可靠依据,猜错就是两个写者同时写一个状态根;A 把「让不让」留给持有者自己答,所以那条硬约定一个字没破。C(产品自己在外面接管)要求产品重写一套「先杀临时实例再起」的逻辑,而那正是 single-writer 语义的一部分,分家出去迟早与 core 的规矩对不上。

硬约定的措辞随之改准(本条补记):**core 不猜对面死没死,也不抢占没有自称可让位的持有者**。两处已改:`packages/core/README.md` 的硬约定、词表 `CONTEXT.md` 的 lease 与「可让位」条目。

登记一条边界(2026-09-07 用户):findjob 这类产品的 session **不会**从终端去 `--resume`,只有它们产品内部会;所以让位发生在同一产品的两个实例之间,不是跨产品。

## 验收

`packages/core/test/lease-handoff.test.ts`(随 e48a366 合入):可让位的持有者在另一方 `acquire` 时收到信号并释放,另一方随后拿到;不可让位的持有者在位时另一方 `acquire` 返回 `null` 且持有者无感知;旧锁文件没有 `preemptible` 字段按不可让位处理。
