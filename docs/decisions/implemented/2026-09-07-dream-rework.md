# dream 改造:范围跟模块声明走、按层各整理各的、加一道水位门单开、从 admission 挪进独立通道

> 状态:implemented · 提出 2026-09-07 · 拍板 2026-09-07(口头) · 实现并合入 2026-09-08 · 相关 [作用域由产品声明](2026-09-07-memory-scopes-by-product.md)、[记忆模块](2026-09-07-memory-modules.md)、[记忆的并发](2026-09-07-memory-concurrency.md)

## 现状(拍板前)

`Agent` 回 idle 时自查门控 → admission 的 maintenance 优先级排一个 run(前台一来就让位:还没跑 → superseded,在跑 → abort)→ 起一个隔离子循环,**只给限定在 session 层的那把记忆工具** → 跑完 [`markDreamed`](../../../packages/core/src/memory/harness.ts#symbol=markDreamed)。

门控四道([`shouldDream`](../../../packages/core/src/memory/harness.ts#symbol=shouldDream),全满足才跑):距上次 ≥24 小时、记忆写入 ≥5 次、轮数、session 层笔记文件 ≥10。范围与状态都把 `"session"` 写死在常量里(`DREAM_SCOPE`、`DREAM_STATE_PATH`)。prompt 五条:去重、剪枝、冲突取证、压进预算、不发明。

## 不拍板的代价

**门的信号选错了轴。** 四道里有两道数的是**记忆活动**(写入次数、文件数),而记忆写入恰恰是我们想促成的**结果**。拿结果当触发条件就是死锁:写得少 → 门不开 → 不整理 → 记忆更没法用 → 写得更少。参照物那边数的是**会话活动**(自上次整理以来被改动的 transcript 数),会话活动一定在发生,所以那道门一定会开。

**范围写死在层名上。** [作用域由产品声明](2026-09-07-memory-scopes-by-product.md) 之后 core 不认识任何具体层名,`DREAM_SCOPE = "session"` 这行没有对象了。而 session 这一层本身也退场了。

**整理跟着"谁能安全独占写"走,而不是跟着"哪里会长胖"走。** 三层切法把 dream 锁死在 session 层,理由是"一段 session 只有一个写者,冲突从结构上没有了"。代价是真正会长胖的共享层(user / project / 角色)没有任何自动整理,只靠"写入超预算被拒"时模型在前台自己收拾。

## 选项

- **A. 只换门控信号**,范围仍限在某个本段独占的层。
- **B. 范围跟模块声明走,共享层也整理**,把多写者保护这笔账还上。
- **C. 保持现状**,等 session 层有人写。

## 决定

**B**(2026-09-07 用户拍板)。C 已被实测证伪。A 回避了真问题:会长胖的就是共享层。

### 整理哪些:模块自己声明

模块定义里一格 `dream: boolean`(见 [记忆模块](2026-09-07-memory-modules.md))。**不由 core 按 `mode` 判**——本记录初稿推荐过"只整理 `indexed`、`resident` 一律不碰",被否:agent 会把不属于某个模块的东西写进去乱放,及时归位比"别碰"更专业。三个内建模块**默认都 `true`**。

### 整理哪几层:它声明的所有层,每层一把整理锁

模块的 `scopes` 里有共享层,所以"两段 session 同时整理同一层"重新成立——三层切法当初结构性消掉的那件事,现在必须正面解。锁不是新机制:今天已经有一把软锁(`startedAt` + `DREAM_LOCK_STALE_MS` 一小时过期),改成**每层目录下各一份**即可。

这把**整理锁**管的是"别做重复功"(两个 dream 把同一层各重排一遍),**不管正确性**——正确性归文件锁,见 [记忆的并发](2026-09-07-memory-concurrency.md)。

### 门:原四道保留,加一道水位,水位单开一条

第五道是**水位**:这一层某个模块的预算用掉 80%。

**水位不与其余四道做 AND。** 两组门的语义相反:24 小时 / 写入数 / 轮数 / 文件数是**节流**("没必要太频繁"),水位是**告警**("再不整理,下一次写入就要被拒了")。AND 连起来等于让节流条件否决告警——恰好在最需要整理的时候不整理,模型只好在前台自己收拾,而那正是我们想用后台换掉的事。所以:**四道 AND,或者水位单独成立。**

原来那两道记忆活动的门保留:提取上线之后记忆写入会真的产生,它们不再是死门。

### 门与状态按层各算各的

整理是按层各整理各的,所以计数、锁、上次时间、水位**各层目录下一份**。`minFiles` 今天只数 `DREAM_SCOPE` 那一层,层名退场后自然变成"每层数自己的"。

唯一的例外是轮数:`turn_end` 是全局事件,按层算没有意义。那道门默认就没开(`DEFAULT_DREAM_GATES` 只有写入数、文件数、间隔三项),先维持不开。

**dream 状态因此不需要单独的落脚点**:它就住在各层自己的目录下,既不用 session 锚点,也不用往状态根搬。

### 从 admission 挪进独立通道

与提取同一条理由(见 [记忆的产生](2026-09-07-memory-extraction.md)):记忆的两件后台活各走各的通道,不来抢主 agent 的执行许可。`admission` 的 `RunSource` 里 `"dream"` 这一支退场,[`assertInternalRunRequest`](../../../packages/core/src/admission/request.ts#symbol=assertInternalRunRequest) 那个显式穷举随之只剩 inbox。

**但 `stop()` 仍要等它收完**——理由不变,见 [记忆的并发](2026-09-07-memory-concurrency.md)。

### prompt 加两条

**归位**(新职责):记在错模块里的内容,在对的模块重建、从原处删除。因为跨模块 rename 禁止(换预算域不许静默发生)、`resident` 模块干脆没有 rename 这个动词,所以这是两步不是一步。

**预算删不下去时删什么**:`resident` 模块预算很紧(2200 / 1400),会出现"合并到头了还是超"的情况。判据是**删最旧且之后没有再被提起过的**——不给判据的话它会随便删。

范围那句从"stay inside session/"改成"stay inside 这一层",层名由调用方填。

再加一条与并发有关的:某个文件改不动(别的 session 正在写)就跳过,不要反复重试。

### 「不发明」这条仍是纪律,不是门

`dream.ts` 那句 "only reorganize what is already there" 今天没有、也不会有机器判据——我们无法验证模型改写记忆时没有编造。三个内建模块默认 `dream: true` 之后,dream 会改写 `agent.md` / `user.md` 这两份 resident 记忆,这条纪律的赌注因此变大。**明确记在这里,不假装它是门。**(本仓口径:只有精确机器判据才叫"守住",其余叫"纪律"。)

## 验收

- 模块声明 `dream: false` → dream 跑完那个模块的所有层零变化。
- 一个模块在两层都有且都 `dream: true` → 两层各自被整理、各自有一份计数与锁,一层的锁被占不挡另一层。
- 两段 session 同时对同一层起 dream → 只有一个真的跑,另一个跳过(拿不到整理锁),两者都不判红。
- 其余四道门全不满足、但某模块索引到 80% → dream 仍然跑(水位单开那条)。
- 距上次整理 <24 小时、水位未到 → 不跑。
- `RunSource` 里不再有 `"dream"`;`assertInternalRunRequest` 只认 inbox。
- dream 在跑时前台发来 prompt → 前台**不等**它(不再是抢占关系),两者同时在飞。
- `stop()` 时在飞的 dream 被中断且等它收完,之后才交出 lease。
- 把一条项目事实手工写进 `agent.md`,跑一次 dream:它被移进笔记模块、`agent.md` 里那段消失。
