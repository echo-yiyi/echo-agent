# Review prompt — 审这套文档门禁机制本身

把下面整段交给一个新的 Claude 会话。**它审的是门,不是被门守的代码。**

---

你在审 `~/Code/echo-agent` 里新加的一套**文档门禁机制**。作者(另一个 Claude)照着 DeepSeek Harness(`~/Code/deepseek-harness`)的门禁设计,给这个即将开源的 agent 内核建了 8 道文档门 + 2 道代码侧门。

**你的任务不是审业务代码,是审这套门本身值不值得留。** 一道立错了的门比没有门更糟:它会持续制造噪音、逼人绕过、最后被整体关掉,连带着好的那几道一起死。

## 先读这些(按顺序)

1. `docs/docs.manifest.json` —— 判据源。所有门都读它
2. `scripts/docs-lint.ts` —— 八道检查的全部逻辑 + 人读报告 CLI
3. `test/docs.test.ts` —— 八道门的测试壳
4. `test/export-jsdoc.test.ts`、`test/spec-refs.test.ts` —— 两道代码侧门
5. `packages/core/scripts/api-inventory.ts` 与 `test/api-snapshot.test.ts` —— **仓库原有的门**,新门声称复用了它的规矩,核实是否属实
6. 跑一次:`bun scripts/docs-lint.ts`,再跑 `bun test test/docs.test.ts test/export-jsdoc.test.ts test/spec-refs.test.ts`

参照系(可选):`~/Code/deepseek-harness/docs/i18n/README.md`(双语配对契约原版)、`~/Code/deepseek-harness/docs/AGENTS.md`(文档分层原版)。**这套是仿制品,你要判断仿得对不对、以及该不该仿。**

## 按这六条判

### 1. 判据可信吗——会不会假绿或假红

对每一道门问:**它绿的时候,能不能推出它声称的那件事成立?红的时候,是不是真的有问题?**

重点查:
- `structuralSignature()` 的粒度够不够——两份结构其实不同的文档会不会算出同一个签名(假绿);两份结构相同的会不会算出不同签名(假红)
- `slug()` 对中文标题的锚点近似,和 GitHub 实际行为差多少
- `checkSections()` 用 `includes()` 匹配标题——「安装」会不会匹配到「重新安装前的注意事项」
- `countWords()` 把中文按字符、西文按词**相加**,这个数有意义吗

### 2. 覆盖与漏洞——该守的守住了吗

- 花名册的野文档扫描**只覆盖 `docs/`**:根目录和 `packages/*/` 下多一份野生 md,门看得见吗
- 双语文档的**中文侧有没有字数预算**(`checkBudgets` 只看 `d.path`)
- `spec-refs` 的正则要求 `§` 后至少两段数字,**单段的 `§15` 这类被静默忽略**——仓库里有一百多处。这是刻意的取舍还是漏洞
- **manifest 本身没有门**:路径重复、`bilingual: true` 的文档同时又被单独登记、tier 拼错——有没有东西拦

### 3. 会不会变成新的谎言源

manifest 现在是「文档结构的契约」。但它自己会不会腐烂?

- 花名册里的**必备小节是作者猜的**(比如 README 定了「安装/快速开始/硬约定/致谢/许可」,而仓库实际用的是「跑起来/两个使用高度/形态由 stdin 决定/目录/License」)。**门正在强制一个没人确认过的骨架** —— 这是最该拍死的一条,还是只要人过一遍就行
- 门的注释里声称的东西(「一份逻辑一个数法」「复用 `inventory()`」),核实是否属实
- **本仓最独特的一条规矩是「『有门守着』和『是纪律』必须分开标,别声称有守」**(见 `packages/core/src/session/types.ts`)。这套新门自己遵守了吗?有没有哪道门的注释声称守住了它实际没守的东西

### 4. 成本

- `checkCodeBlocks()` 每次跑都 spawn 一次 `tsc`(约 1 秒),而且**在仓库根 `rm -rf` 一个固定名字的目录**。这个设计安全吗、值吗
- `blobHash()` 对每个双语文件 spawn 一次 `git`——文档多了会怎样;没有 `.git` 的环境(tarball、某些 CI)会怎样
- 八道门的总耗时,对「每次改文档都要跑」这个使用频率合不合适

### 5. 可执行性——红了之后人会怎么做

- **JSDoc 门现在 273 条缺口**(519 个公共符号,246 个有 JSDoc)。一道注定长期红的门,和没有门,区别是什么?棘轮(记 baseline、只拦新增)是不是唯一现实的选择
- `spec-refs` 依赖一份**目前不在本仓**的规格文档。在它搬进来之前,这道门只会输出同一条错误——这期间它有价值吗
- 花名册要求 5 份还不存在的文档。门当工单用,合理吗;还是应该分「必须有」和「计划有」两档

### 6. 和既有门的关系

- 仓库原有 48 个测试里已有 `api-snapshot` / `engine-purity` / `zero-runtime-deps` / `package-isolation` / `distribution-gate` / `invariants`。新门有没有**重复**已有覆盖
- 有没有**冲突**:两道门对同一件事给出不同判据
- 新门该不该进 `package.json` 的 `test` 脚本(现在靠 `bun test` 自动收集)、该不该进 CI

## 输出

分三段:

**A. 留哪些** —— 逐道门给「留 / 改 / 删」,一句话理由。改的说清改什么。

**B. 缺哪些** —— 这个仓库该有但这套没建的门。**只列你能说清判据的**;说不清怎么机器判的,归到 C。

**C. 不该用门解决的** —— 有些东西只能靠人审。明确列出来,免得后来者以为门覆盖了。

结尾一段:**如果只能留三道,留哪三道?** 理由。

## 纪律

- 每条判断落到 `file:line` 或一条可复现的命令。**跑一下再说**,别只读代码猜行为。
- 作者已知的弱点在上面列了一部分。**找出他没列的那些才是这次审的价值。**
- 「可以加个 X」不算发现,除非你能说清它的判据和它拦住的具体失败。
- 一条有证据的「这道门会假绿」,胜过十条「建议增强」。
