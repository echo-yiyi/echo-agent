## 这个仓库的判据(不是通用最佳实践)

作者自己立的规矩,评审按这些判,不按你习惯的那套:

- **零运行时依赖。** `packages/core` 的 `dependencies` 恒空,有门守着。
- **fail-loud,绝不静默降级。** 缺凭据、拿不到锁、盘上坏档——一律抛。**「装了一半」比「起不来」更糟**。
- **single-writer。** 一个状态根同时只允许一个写者;锁被占就拒绝启动,**core 不抢占**、不猜对面死没死。
- **`write()` resolve 即持久。** 存储端口上没有 `flush`。
- **一次写失败就封存该会话**,拒绝继续写——继续写只会产出坏档。
- **`/engine` 面纯 Web 标准**,任何 `node:` 倒灌即红。
- **一份逻辑,一个数法。** 同一件事不许有第二套实现(见 `api-inventory.ts` 的先例)。
- **「有门守着」和「是纪律」必须分开标。** 这是本仓最独特的一条:注释里声称有保障、实际没有门的地方,**按缺陷报**。原话是「如实标注,别声称有守」。

## 优先找这几类缺陷(按这个仓库的真实风险排序)

1. **所有权与释放。** 谁负责 dispose、什么时候转移、转移是不是原子的。构造失败/中途 abort 的窗口里,已经造好的资源有没有人关;会不会关两次(`StorageDir.close()` 的契约没要求幂等)。参照 `assembly/ledger.ts` 的 adopt/borrow 二分。
2. **异步窗口。** 每一个 `await` 前后:状态还是不是原来那个?锁还在不在?被 abort 了会怎样?**「await 回来之后不重新校验」是本类第一号 bug**。
3. **持久化正确性。** 崩在半路留下什么;恢复时读到不完整的东西会怎样;封存之后的行为;`parent` 指向不存在 entry 的坏档能不能被造出来。
4. **观测不得影响执行。** 观测路径上的异常、背压、ring 满,都不能让主循环变慢或失败。`offer()` 声称同步、永不抛、无 Promise —— **逐条验证它真的做到**。
5. **边界与限额。** 尺寸/时间/条数限制作用在**最终产物**上,还是只作用在中间值上;多字节字符按字节截断会不会切坏。
6. **模型可见面。** 发给模型的 prompt、工具 schema、错误文本:有没有混进实现术语、传输细节、内部 ID。模型只该看见任务相关的概念。
7. **路径安全。** 任何进入文件路径的外部输入(agentId / sessionId / 文件名)是否都过了校验——**防线漏在哪一处,就从哪一处漏掉全部**。

## 别报这些

- 已经有门守着的(先看 `test/` 有没有对应的门;有门还报就是噪音)
- 纯风格、命名偏好、格式
- 「可以加个抽象层」「将来可能需要」——这个仓库明确反对投机性通用化
- 你没读过对应代码就凭直觉猜的

## 输出格式

每条发现一段,按严重度降序:

```
### [P1|P2|N] 一句话结论

**证据**  file.ts:123-130,贴关键几行
**问题**  具体会怎么错:什么输入/时序 → 什么后果
**判据**  违反了上面哪条硬约定,或哪个契约与实现不符
**建议**  最小改法(不要重设计)
```

- `P1` = 开源前必须修 / 会导致数据损坏或静默错误
- `P2` = 值得排期
- `N` = 记录在案,不必动

**结尾必须有一段「我没能验证的部分」**:范围内你读了但没把握的地方、需要跑起来才能确认的假设。宁可列出来,也不要假装看懂了。

## 纪律

- 每条断言都要能落到 `file:line`。读不到就说读不到,**不要从文件名或注释推测行为**。
- 注释和代码不一致时,**以代码为准**,并把这个不一致本身报成一条发现。
- 拿不准是不是 bug 时,写成「需要确认:如果 X 成立则……」,不要为了凑数报成缺陷。
- 一条有证据的 P1,胜过十条 P2。
